2. System Architecture

Principal's Take: The architecture is well-layered but tightly coupled at the Substrait boundary. The single-backend constraint (exactly one SubstraitBackend per JVM) is a significant design limitation for GPU hybrid execution. The backend abstraction is too coarse-grained — it operates at the plan level, not the operator level. GPU enablement will require breaking this into operator-level backend selection.

5. Spark vs Gluten vs Velox — Responsibility Map

Principal's Take: The tri-party boundary creates a complex dependency chain. Gluten's daily Velox version bumps are both a strength (staying current) and a risk (any Velox API break cascades immediately). The tightest coupling is the Substrait → Velox plan conversion, which embeds deep assumptions about Velox's operator model. For GPU, the coupling gets worse: Velox's experimental cuDF path is itself unstable, and Gluten must track both Velox main AND Velox cuDF experimental changes.

Tight Coupling Risks

HIGH — Velox API Surface

  • Daily Velox bumps mean any API change breaks Gluten
  • SubstraitToVeloxPlan.cc embeds Velox PlanNode hierarchy knowledge
  • No Velox stable release cadence — Gluten tracks HEAD

HIGH — GPU Memory Model

  • RMM pool is global and separate from Spark's memory system
  • No back-pressure from GPU memory to Spark's off-heap budget
  • GPU OOM crashes the JVM without graceful fallback

MEDIUM — Substrait as Single IR

  • Substrait v0.23.0 base with Gluten-specific extensions
  • Backend-specific behavior in "extension" fields — not standardized
  • No GPU-specific plan annotations in Substrait spec

MEDIUM — Single Backend Constraint

  • BackendsApiManager enforces exactly one SubstraitBackend per JVM
  • Cannot run Velox-CPU and Velox-GPU as separate backends
  • GPU/CPU hybrid must happen within single Velox backend

Abstraction Leaks

  • Velox-specific configs exposed in Spark: spark.gluten.sql.columnar.backend.velox.* — 50+ settings leak Velox internals
  • Arrow format dependency: Columnar batch assumes Arrow ABI; ClickHouse uses different block format
  • GPU conditional compilation: #ifdef GLUTEN_ENABLE_GPU scattered across JNI/native code
  • Shuffle format lock-in: Velox shuffle uses Presto serializer — not interchangeable with other backends

6. GPU Extension Feasibility Analysis

Principal's Take: GPU support through Velox's experimental cuDF path is the right strategic choice — it avoids building a separate GPU backend and leverages existing Substrait translation. However, the current implementation has three critical gaps: (1) no GPU table scan means data must enter via CPU, (2) RMM memory is invisible to Spark's memory manager creating OOM risk, and (3) CPU↔GPU data movement on every fallback nullifies performance gains. The 8.1x speedup on TPC-H is promising but only for cherry-picked compute-heavy queries.

Key Technical Challenges

1. JVM → Native → GPU Memory Transitions

  • Current: Spark (JVM) → Gluten off-heap (ReservationListener) → Velox MemoryPool → RMM (device memory)
  • Problem: Three memory domains with no unified back-pressure. GPU failure can't propagate to Spark for spill.
  • Risk: HIGH — GPU OOM causes process crash, not graceful task failure.
  • Mitigation: Integrate RMM callbacks into SparkAllocationListener chain; implement GPU spill to host.

2. Substrait Plan Compatibility with GPU

  • Current: Same plan sent to native; CudfPlanValidator checks GPU capability; unsupported stays on CPU.
  • Problem: Validation is binary. No cost-based "is GPU faster for this data size?" decision.
  • Risk: MEDIUM — Small batches on GPU may be slower due to kernel launch overhead.

3. Operator Coverage Gaps

  • Critical: Scan not on GPU → every pipeline starts with CPU-to-GPU transfer
  • Critical: Window functions not on GPU → complex analytics fall back entirely
  • High: SortMergeJoin not on GPU → large fact-dimension joins can't use GPU

4. CPU ↔ GPU Data Movement

  • Problem: PCIe bandwidth (32 GB/s Gen4 x16) becomes bottleneck for large intermediates
  • Risk: HIGH — Each transition adds latency; mixed pipelines may be net-negative.
  • Mitigation: Group GPU-compatible operators; pin data to GPU for multi-stage pipelines.

5. Mixed Cluster Scheduling

  • Issue #11524: GPU and CPU mixed cluster scheduling not supported
  • Issue #11828: GPU code runs on CPU nodes when cudf enabled
  • Risk: MEDIUM — Deployment complexity and resource waste.

7. Module Importance & Effort Analysis

Principal's Take: The highest-leverage investment for GPU enablement is the memory management layer — getting RMM integrated with Spark's memory system unlocks everything else. The highest-risk area is the Substrait translation layer, which needs operator-level device annotations without breaking CPU-only compatibility. The shuffle layer is surprisingly well-positioned: GPU shuffle writer/reader already exist, just need stabilization.

8. Phased Roadmap for GPU Enablement

Principal's Take: The roadmap must be pragmatic. Phase 1 focuses on making existing GPU operators production-safe (memory, scheduling, CI). Phase 2 tackles the hard architecture problem of hybrid execution. Phase 3 is aspirational and depends heavily on Velox upstream maturity. Each phase has a clear gate: don't advance until the previous phase's validation criteria are met. I estimate 6-8 months per phase for a team of 3-4 engineers, with significant Velox upstream dependency.

The biggest non-technical risk is organizational: this work spans Gluten, Velox, and RAPIDS teams — alignment on priorities is as important as the code itself.
