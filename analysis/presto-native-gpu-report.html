Data Flow: SQL → Results

1. SQL → Java Coordinator (parse, analyze, optimize, generate distributed plan)
2. Coordinator sends JSON plan fragments to native workers via HTTP REST (/v1/task/{taskId})
3. TaskResource deserializes JSON → protocol::PlanFragment
4. VeloxQueryPlanConverter walks protocol plan tree via dynamic_pointer_cast dispatch (25+ node types)
5. Each protocol node maps to a Velox core::PlanNode
6. Root OutputNode synthesized as Velox PartitionedOutputNode
7. Velox creates Task → Driver pipelines → Operators execute on vectorized column batches
8. (GPU path): CudfDriverAdapter rewrites operator chain at compile time, inserting CudfFromVelox/CudfToVelox at CPU↔GPU boundaries
9. Results returned via HTTP to coordinator or downstream exchange

Coupling Risk Assessment

Interface PointCouplingRiskAnalysis
Velox Submodule Pin High High Frequent "Advance Velox" commits (~monthly). API changes cascade. The submodule tracks near-HEAD. GPU features in Velox are available immediately but breaking changes propagate instantly.
Plan Node Dispatch Medium Medium 25+ node types via dynamic_pointer_cast chain in a 2,602-line file. New Velox plan nodes require manual Presto translation additions. Fragile but well-understood pattern.
Operator Registration Low Low Well-defined registration API (registerOperator, registerExchangeSource). Custom operators are purely additive. GPU DriverAdapter hooks in cleanly.
Memory Model High High Direct use of Velox MemoryManager and SharedArbitrator. Config mapping required. GPU adds second memory system (RMM) without unified pressure signaling. Highest coupling risk for GPU path.
Connector Interface Medium Medium Bridge pattern (PrestoToVeloxConnector) provides abstraction, but implementations tightly coupled to Velox HiveConnector internals (split types, handle types).
cuDF Build Integration Medium Medium PRESTO_ENABLE_CUDF flag propagated to VELOX_ENABLE_CUDF. CMake coordination required. GCC 14+ requirement when cuDF enabled adds build matrix complexity.
Key Insight: Presto Native's thin-layer architecture is simultaneously its greatest strength and its GPU enablement advantage. Since the heavy lifting (operator execution, memory management, I/O) lives in Velox, GPU support in Velox's experimental/cudf/ module propagates to Presto Native with minimal additional Presto-layer work. The Presto-specific work is: session config wiring, plan validation, and sidecar GPU awareness. The hard GPU engineering is entirely in Velox.

06GPU Integration Design

GPU acceleration leverages Velox's cuDF experimental module. The design uses a DriverAdapter pattern — a compile-time rewrite of the operator chain that substitutes CPU operators with GPU equivalents and inserts conversion operators at boundaries.

Current GPU Operator Coverage

Implemented (8 operators)
  • CudfFilterProject — AST/JIT GPU expression eval
  • CudfHashAggregation — Grouped & global aggregations
  • CudfHashJoin — Build + Probe (partial)
  • CudfOrderBy — GPU parallel sort
  • CudfTopN — GPU top-N selection
  • CudfLimit — GPU limit
  • CudfLocalPartition — GPU partitioning
  • CudfAssignUniqueId — GPU unique ID
Infrastructure Operators (3)
  • CudfFromVelox — CPU→GPU conversion
    Velox RowVector → Arrow C ABI → cudf::table
  • CudfToVelox — GPU→CPU conversion
    cudf::to_arrow_host → Velox RowVector
  • CudfBatchConcat — Batches small inputs before GPU aggregation
Missing for GPU
  • Window Functions
  • MergeJoin / SemiJoin / SpatialJoin
  • Unnest / GroupId
  • RowNumber / TopNRowNumber
  • MarkDistinct / DistinctLimit
  • Exchange (GPU-aware)
  • TableWriter (tests disabled)

GPU Hook Points in Architecture

Hook PointMechanismStatusRisk
Operator Substitution OperatorAdapterRegistry — adapters registered per CPU operator type. CudfDriverAdapter::compile() walks operator list and replaces using adapter's createReplacements(). Working Low
CPU↔GPU Conversion CudfFromVelox/CudfToVelox auto-inserted at boundaries. Uses Arrow C ABI bridge: exportToArrow() → cudf::from_arrow() and reverse. Working Medium
GPU Connector CudfHiveConnectorFactory replaces HiveConnectorFactory when PRESTO_ENABLE_CUDF. Parquet read directly to GPU memory via cudf::io::parquet. Working Medium
GPU Memory RMM (RAPIDS Memory Manager) with configurable backends: pool, async, arena, managed, prefetch. Separate output_mr and temp_mr. Working High
Session Config cudf.enabled query config gates GPU activation. PR #27204 adds Presto-layer session property provider. In Progress Low
Plan Validation PR #27273 adds CudfPlanChecker. Validates plan fragment GPU-eligibility before execution. In Progress Low
Sidecar GPU Extension PR #27164 extends sidecar plugin so coordinator knows about GPU capability — enables GPU-aware task routing. In Progress Medium

Critical Design Risks

Arrow C ABI as CPU↔GPU bridge adds per-batch serialization cost. For batches under ~10K rows, conversion overhead may exceed GPU compute benefit. CudfBatchConcat mitigates for aggregation but no universal solution exists.
GPU memory (RMM) is completely separate from Velox's MemoryManager/SharedArbitrator. No unified memory pressure signaling exists. GPU OOM will crash the worker rather than triggering spill.
Dynamic filters are NYI in CudfHiveDataSource. Queries relying on dynamic filtering will either fall back to CPU or execute suboptimal full-table GPU scans.
Exchange/shuffle is CPU-only. Data must be converted GPU→CPU before every exchange and CPU→GPU after. Multi-stage join queries will see significant boundary conversion overhead.
Null-aware anti-join with filter is explicitly disabled in CudfHashJoinBaseAdapter. Certain TPC-DS queries will fall back to CPU execution.
Type coverage: MAP types, some interval types, VARBINARY (exported as string for cuDF) are incomplete on GPU. Complex nested type queries will trigger unexpected fallbacks.
Design Principle: The cuDF integration follows a "progressive replacement" model. The DriverAdapter walks the operator chain and replaces what it can, inserting conversion operators at boundaries. The allowCpuFallback flag controls whether unsupported operators trigger an error or fall back to CPU. This is architecturally sound — it means partial GPU execution is always possible, and GPU coverage can be incrementally expanded.

08GPU Enablement Roadmap

Three-phase roadmap from minimal GPU execution through hybrid CPU+GPU to full acceleration. Each phase is independently valuable and deployable.

Phase 1: Minimal GPU Execution

Q2–Q3 2026 · 3–4 months

Goal: End-to-end GPU execution for scan → filter → aggregate queries on Parquet data. Prove the Presto↔Velox↔cuDF integration works through TPC-H subset.

Components to Build

  • cuDF Session Property Provider — Wire cudf.enabled through Presto session props (PR #27204)
  • CudfPlanChecker integration — Validate plan GPU-eligibility in TaskResource before creating tasks (PR #27273, #27275)
  • GPU CI pipeline — cuDF in native e2e tests on GPU hardware (PR #27369)
  • Sidecar GPU awareness — Coordinator knows which workers have GPU capability (PR #27164)
  • Fallback mechanism — allowCpuFallback=true for unsupported operators; log fallback events for visibility
  • Monitoring — GPU utilization, conversion overhead, and fallback rate metrics

Validation Strategy

  • TPC-H Q1, Q3, Q5, Q6, Q10 (cover scan + filter + agg + join patterns)
  • Correctness: bit-exact results vs CPU-only execution
  • Performance: measure wall-clock speedup on SF100 and SF1000
  • Memory: monitor GPU memory high-water mark, validate no leaks
  • Fallback: verify graceful degradation for unsupported plan fragments

Key Risks

Arrow conversion overhead may negate GPU benefit for small datasets. Minimum viable batch size needed.
Expression coverage gaps in AST/JIT evaluator for complex Presto scalar functions.

Phase 2: Hybrid CPU+GPU Execution

Q4 2026 – Q2 2027 · 4–6 months

Goal: Robust hybrid execution where GPU and CPU operators coexist within the same query. Smart routing decisions. Full TPC-H coverage with minimal fallback.

Components to Build

  • Intelligent plan routing — Cost model: GPU vs CPU per fragment based on data size, operator mix, GPU memory availability
  • Dynamic filter GPU support — Implement addDynamicFilter in CudfHiveDataSource
  • GPU Window functions — CudfWindow operator using cudf::grouped_rolling_window
  • Unified memory pressure — Bridge RMM OOM callbacks to Velox SharedArbitrator for coordinated memory management
  • GPU spill (basic) — GPU→CPU→disk path for aggregation and join spill under memory pressure
  • Complete anti-join — Null-aware anti-join with filter in CudfHashJoin
  • Iceberg GPU path — Extend CudfHiveDataSource pattern to Iceberg Parquet reads
  • Type coverage — MAP types, interval types, VARBINARY proper handling

Validation Strategy

  • Full TPC-H (22 queries) at SF1000 — target ≥18 queries fully on GPU
  • TPC-DS representative subset (30+ queries)
  • Mixed workload testing: GPU + CPU queries running concurrently
  • Memory pressure: trigger spill under GPU memory limits, verify correctness
  • Full TPC-DS 99 queries produce correct results (fallback allowed)

Key Risks

Coordinating CPU and GPU memory arbitration is architecturally novel — potential for deadlock or resource starvation.
GPU spill path (GPU→CPU→disk) performance may be worse than CPU-only for some query shapes, requiring smart routing to avoid.

Phase 3: Full GPU Acceleration

Q3 2027+ · 6–12 months

Goal: End-to-end GPU execution for the majority of production queries. Multi-GPU scaling. GPU-aware network exchange. Production-grade reliability and performance.

Components to Build

  • GPU-aware exchange — UCX or GPUDirect RDMA for GPU→GPU data transfer between workers, eliminating D2H/H2D at shuffle boundaries
  • Multi-GPU support — Data partitioning across GPUs within a worker. GPU-affinity-aware task scheduling
  • GPU TableWriter — Re-enable and complete GPU write path using cuDF Parquet writer
  • Complete operator coverage — MergeJoin, SemiJoin, Unnest, GroupId, RowNumber, TopNRowNumber, MarkDistinct on GPU
  • GPU-native spill — Direct GPU→NVMe via GDS (GPU Direct Storage) or cuFile
  • Adaptive execution — Runtime GPU↔CPU migration based on actual performance signals and resource utilization
  • CUDA MPS / MIG — Multi-tenant GPU sharing with compute and memory isolation

Validation Strategy

  • Full TPC-DS 99 queries on GPU (minimal fallback, target ≥90)
  • Production workload replay testing from real clusters
  • Multi-GPU scaling efficiency (near-linear on 2/4/8 GPUs)
  • 24/7 stability testing under sustained mixed workloads
  • TCO comparison: GPU worker cluster vs CPU-only at equivalent $/query

Dependencies

  • UCX integration in Velox exchange layer (does not exist today)
  • cuDF window function maturity for full Presto frame semantics
  • RAPIDS 26.x+ feature completeness for all aggregation types
  • CUDA driver + GDS support in target deployment environment
  • Network infrastructure supporting GPUDirect RDMA (RoCE/InfiniBand)

Decision Framework

Recommendation: Phase 1 is immediately executable — all key PRs are in flight (#27204, #27273, #27275, #27369, #27164). The primary gating factor is GPU test infrastructure and validation throughput. Begin Phase 2 design in parallel, with unified memory management as the highest-risk item requiring early prototyping.

Key Architectural Advantage: Presto Native's thin-layer-over-Velox architecture means GPU support in velox/experimental/cudf/ propagates to Presto with minimal Presto-specific engineering. The Presto layer work is configuration, validation, and session management. The hard GPU engineering lives entirely in Velox.

Go/No-Go Criteria for Phase 2:
✓ TPC-H Q1+Q6 produce correct results end-to-end on GPU
✓ GPU execution is ≥2x faster than CPU for qualifying queries at SF100
✓ Fallback mechanism works reliably — no crashes, no silent wrong results
✓ GPU CI pipeline runs green for 2+ weeks continuously
