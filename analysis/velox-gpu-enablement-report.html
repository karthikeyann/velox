How Velox Got Here

The project evolved through four distinct phases. Each phase left architectural decisions that shape what cuDF can and cannot do today. ● = inflection points.

Phase 1: Foundation (2021)
Meta open-sources the execution engine from Presto
Shipped Day 1 with a complete pipeline-based execution engine: Task/Driver/Operator model, Hive connector, DWRF file reader, expression compiler, Presto function library, and a columnar vector format with dictionary/constant/lazy encodings. Already battle-tested at Meta scale.
Architecture locked in early: the Operator interface (addInput/getOutput), the Driver pipeline model, and RowVector as the unit of data flow. cuDF must work within these, not replace them.
Key Decision: Operator as the abstraction boundary
Each operator is a self-contained unit with typed input/output
Unlike systems that fuse operators into compiled pipelines (e.g., HyPer/Umbra), Velox keeps operators as distinct objects that a Driver iterates over. Data flows as RowVector batches between operators.
This is exactly why cuDF integration works: you can swap individual operators without touching the pipeline. DriverAdapter exploits this boundary. If Velox had chosen whole-pipeline codegen, GPU integration would be orders of magnitude harder.
Phase 2: Ecosystem Growth (2022 — 2,914 commits)
Multi-engine adoption: Presto, Spark (Gluten), Trino
Spark adoption via Gluten drives a parallel Spark SQL function library (200+ functions). DuckDB bridge added for SQL parsing. Native Parquet reader development begins. External contributors grow rapidly. Velox becomes a library, not just a Presto component.
Dual-dialect function library (Presto + Spark) doubles the GPU expression coverage problem. Any function that cuDF supports must work with both Presto and Spark semantics. The function registry abstraction makes this manageable but the surface area is large.
Key Decision: Hierarchical Memory with Arbitration (2022-H2)
MemoryPool tree: query → task → node → operator
A 4-level pool hierarchy where each operator gets a scoped allocator, tasks can be killed under memory pressure, and an arbitrator mediates between competing queries. This enables multi-tenant execution without OOM.
This is the single most important abstraction for GPU planning. GPU memory (managed by RMM) currently lives outside this hierarchy entirely. Velox's arbitrator has zero visibility into GPU memory. Bridging these two worlds is the hardest problem in the cuDF roadmap.
Phase 3: Production Hardening (2023 — 3,251 commits, peak year)
Spill, SSD cache, Iceberg, comprehensive fuzz testing
Spill-to-disk for hash joins and aggregation. SSD-backed async data cache with TTL. Iceberg V2 in the Hive connector. TypeSignature parser via Flex/Bison. The fuzz testing framework (join, aggregation, expression fuzzers) becomes a gatekeeper for correctness.
The spill framework is CPU-only (serializes to disk via RowVector). cuDF cannot reuse it directly; GPU spill needs device→host serialization first. The fuzz testing infrastructure is essential for cuDF quality but not yet integrated with GPU operators.
2023-08: Wave GPU Experiment
First GPU attempt: custom CUDA kernels (43K LoC)
Custom WaveVector format, GPU arena allocator, hand-written CUDA kernels for decode/filter/project/aggregate. Targets maximum throughput for IO-heavy workloads. Nimble format GPU decode. Required CUDA expertise for every new operator.
Wave proved GPU execution is viable in Velox but showed the maintenance cost of custom kernels is prohibitive for broad operator coverage. This directly motivated the cuDF pivot: use a library instead of writing kernels.
Phase 4: GPU Acceleration (2025–present)
cuDF backend via DriverAdapter — library over kernels
Strategic pivot from custom CUDA (Wave) to RAPIDS libcudf. DriverAdapter rewrites operators at compile time. 12+ GPU operators in <1 year (OrderBy, HashAgg, HashJoin, FilterProject, TopN, Limit, LocalPartition, Window, Expand, NestedLoopJoin, AssignUniqueId). CudfHiveConnector for GPU-direct Parquet reads. AST + JIT expression evaluation on device.
The DriverAdapter abstraction (added for Wave) made cuDF integration possible without modifying core Velox. This was not designed for cuDF specifically — it's a general operator-rewriting hook. cuDF's rapid progress validates the architectural decision.
Key Decision: DriverAdapter as the GPU seam
Operators swap transparently; plan IR stays device-agnostic
CudfDriverAdapter inspects each driver's operator list and replaces CPU operators with GPU equivalents. CudfFromVelox/CudfToVelox conversion operators are inserted at CPU↔GPU boundaries. The plan IR (PlanNode) never knows about GPU.
This is clean but has limits: the adapter can only replace whole operators, not fuse them. GPU-optimal execution sometimes wants to fuse scan+filter+project, but Velox's operator boundaries prevent this. cuDF must work within the granularity Velox gives.

Key Abstractions (What cuDF Plugs Into)

Operator exec/Operator.h

The compute unit. addInput(RowVector) → process → getOutput() → RowVector. Every GPU operator inherits this. The cuDF path creates GPU equivalents that accept/produce CudfVector (a RowVector subclass wrapping cudf::table).

Driver exec/Driver.h

Runs a pipeline: an ordered list of operators. Iterates calling getOutput on source, feeding through the chain. DriverAdapter is the hook that cuDF uses to rewrite this list before execution starts.

Task exec/Task.h

Owns a PlanFragment, creates Drivers for each pipeline, manages lifecycle and memory. Serial or parallel execution modes. cuDF does not modify Task — it operates purely at the Driver/Operator level.

DriverAdapter exec/Driver.h

The GPU integration seam. Registered globally via DriverFactory::registerAdapter. Inspects each driver's operator list and can replace, remove, or insert operators. CudfDriverAdapter uses this to swap CPU operators for GPU equivalents and insert conversion boundaries.

MemoryPool common/memory/MemoryPool.h

4-level hierarchy: root → query → task → operator. Tracks allocations, enforces limits, supports arbitration. GPU memory (RMM) is entirely outside this tree. This is the architectural gap cuDF must eventually bridge.

Connector / DataSource connectors/Connector.h

Abstract interface: addSplit, next() → RowVector. CudfHiveConnector extends HiveConnector to use cuDF's Parquet reader, keeping data on GPU from the start.

Data Flow: CPU vs GPU Path

CPU Path (default): Parquet file → DWIO reader → RowVector → Filter → Project → HashJoin → Aggregate → result CPU memory throughout, managed by MemoryPool GPU Path (cuDF): Parquet file → cuDF Parquet IO → CudfVector → CudfFilter → CudfProject → CudfHashJoin → CudfAgg → CudfToVelox → result GPU memory (RMM), conversion at boundaries only Mixed Path (fallback): Parquet → cuDF scan → CudfVector → CudfFilter → CudfToVelox → CPU HashJoin → CudfFromVelox → CudfAgg → result Conversion operators inserted automatically where GPU can't handle an operator

What This Means for Velox-cuDF Planning

Architecture Gives You

Clean operator swaps via DriverAdapter

Each GPU operator is isolated, testable, and doesn't affect CPU path. You can add operators incrementally. The adapter pattern means cuDF is purely additive — it can't break existing Velox behavior.

Device-agnostic plan IR

PlanNode/QueryCtx know nothing about GPU. This means cuDF doesn't need upstream changes to core Velox for basic operator support. You can ship GPU features without coordinating plan-level changes.

CudfVector fits the existing contract

Subclassing RowVector means GPU data can flow through the existing pipeline machinery (Driver iteration, stats collection, pipeline splits) without modifications.

Automatic CPU fallback

The adapter inserts CudfFromVelox/CudfToVelox conversion operators at GPU↔CPU boundaries. Any operator the GPU can't handle simply stays CPU. This makes partial GPU coverage viable from Day 1.

Architecture Constrains You

No operator fusion

Velox's operator-per-node model means you can't fuse scan+filter+project into a single GPU kernel. Each operator launches its own cuDF calls. The overhead is small for large batches but matters for high-selectivity queries with small intermediates.

Memory is split-brain

MemoryPool tracks CPU. RMM tracks GPU. Under memory pressure, Velox's arbitrator will kill a query that's consuming GPU memory it can't see, or fail to kill one that's hoarding GPU memory. This is the biggest production risk.

Spill is CPU-only

Velox's spill framework serializes RowVectors to disk. GPU data must first transfer to host. There's no device→disk path. Under GPU memory pressure, the only option today is full CPU fallback, not graceful spill.

Expression coverage is a gating factor

A single unsupported function in a FilterProject expression forces the entire operator to CPU. This is all-or-nothing at the expression level, not per-function. The practical GPU coverage of real queries depends more on expression support than operator support.

Recommended Planning Priorities

NEAR-TERM Maximize query coverage on GPU

The architecture supports incremental operator addition with zero risk to CPU path. Focus on:

  • Expression coverage over operator coverage. You have 12 operators. A query that uses HashJoin but has an unsupported function in FilterProject will still fall back to CPU for the filter. Profile real workloads to find the top-30 functions blocking GPU execution, then port those.
  • Remaining high-value operators: EnforceSingleRow (unblocks subquery patterns), RowNumber (common in analytics), full Window support.
  • GPU CI in mainline. 828 commits/year to exec/ means the Operator interface, Driver lifecycle, and DriverAdapter could change under you. Without CI, you're debugging regressions manually.
MID-TERM Production readiness

The dual-memory-world is the architectural ceiling. Tackle it before production deployment:

  • GPU memory visibility: Bridge RMM failure callbacks to MemoryArbitrator. Start with advisory limits (GPU usage reported to Velox, soft enforcement), not hard integration. This is a multi-quarter project.
  • GPU spill: Device→host spill for hash tables. Reuse Velox's spill file management but serialize from GPU memory directly. This unblocks large-data workloads that exceed GPU memory.
  • Dynamic filter pushdown: Currently disabled in CudfHiveConnector. Star-schema queries (common in analytics) rely on this for performance. Requires GPU-side bloom filter support.
  • Fuzz testing: Integrate existing join/aggregation/expression fuzzers with CudfDriverAdapter. This will find bugs you can't find with hand-written tests.
LONG-TERM Advanced optimization

Only after single-GPU execution is production-stable:

  • Cost-based GPU/CPU decision: Not all operators benefit from GPU (small cardinality, high selectivity). An operator-level cost model that routes to GPU only when beneficial. Requires profiling data from production workloads.
  • Multi-GPU: NCCL-based exchange for multi-GPU nodes. Partition-aware placement. Only matters for workloads that don't fit in a single GPU's memory after spill.
  • Operator fusion: If the Velox operator boundary becomes a bottleneck, consider proposing upstream changes to support fused scan+filter+project as a single compound operator. This requires Velox community buy-in.
Bottom line: Velox's architecture is well-suited for GPU integration at the operator level. The DriverAdapter pattern was the right design choice and cuDF is exploiting it effectively. The two areas where the architecture will fight you are (1) expression coverage (all-or-nothing per operator, long tail of functions) and (2) memory management (split-brain between CPU and GPU). Expression coverage determines how many queries actually run on GPU. Memory integration determines whether those queries survive production workloads. Plan accordingly: expressions first, memory second, everything else is incremental.
