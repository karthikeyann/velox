Reading this matrix for cuDF planning: Focus on rows where cuDF Complexity is High and Maturity is Production. These are features that real workloads depend on heavily but are hard to GPU-accelerate: FilterProject (expression coverage), Exchange (GPU shuffle), Spill (GPU memory overflow), MemoryPool/Arbitration (unified pressure). The Low complexity items are either done or don't need GPU work — don't spend time there. The None items (DWRF, ORC, cache, trace) should stay CPU permanently.

Sub-features: Local exchange · Remote exchange (Presto wire protocol) · MergeExchange · Broadcast · PartitionedOutput · Shuffle compression · Checksum · OutputBuffer spill

Sub-features: HashJoin spill · Aggregation spill · OrderBy spill · Window spill · RowNumber spill · MarkDistinct spill · OutputBuffer spill · Async merge · Multi-round merge · Concatenate files merge stream

cuDF gap: No GPU spill at all. Full CPU fallback is the only option under GPU memory pressure.

Expression & Function Detail

Expression Evaluation Architecture

CPU path: ITypedExpr → ExprCompiler → Expr DAG → EvalCtx → VectorFunction calls → RowVector output

GPU path: ITypedExpr → CudfExpression framework (priority-based selection):

  • ASTExpression: Translates to cudf::ast::tree. Covers arithmetic, comparisons, logical ops, simple casts. Fastest path.
  • JitExpression: JIT-compiled GPU kernels for expressions not in cuDF AST. Broader coverage, higher compile cost.
  • CudfFunction registry: Per-function GPU implementations (e.g., date_format, casts). Manual mapping.
  • Fallback: If none match, entire FilterProject falls back to CPU.

Function porting strategy: The top-4 categories by query coverage (Math, Comparison, Date/Time, String) account for ~80% of expressions in typical OLAP workloads. These are where cuDF should invest. Array/Map lambdas are architecturally hard (GPU doesn't do per-element callbacks well). JSON/URL/Geospatial/HLL are niche — leave on CPU.

GPU Memory (Current State in cuDF)

RMM (RAPIDS Memory Manager): Device memory allocation. Modes: cuda (raw), pool, async (default), arena, managed, managed_pool. Configurable via cudf.memory_resource config.

Output MR: Separate resource for operator output allocations (cudf.output_mr config).

Pinned Pool: Auto-sizing with 8GB minimum. PreferredPinnedPool for graceful pageable fallback.

Stream Pool: cuDF stream pool for concurrent GPU operations (cudfGlobalStreamPool).

What's missing: No visibility into Velox's MemoryArbitrator. No device-to-host spill. No memory budget enforcement at query level for GPU. No cross-device memory pressure signaling.
