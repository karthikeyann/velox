Type System Architecture Comparison

Velox Type System

  • Two-tier design: Physical TypeKind enum + Logical subclasses
  • 18 TypeKind values define storage layout and vector encoding
  • Logical overlay: DATE, DECIMAL, INTERVAL, TIME share a TypeKind
  • Backing types: bool, int8–64, int128, float, double, StringView, Timestamp
  • No unsigned integers in the type system
  • Single TIMESTAMP with (seconds, nanos) struct pair
  • Dictionary encoding at vector level (DictionaryVector), not type level
  • Extension types via name() + C++ class identity (18 Presto types)
  • Type factory: TypeFactory<KIND> + helpers like INTEGER(), DECIMAL(p,s)

cuDF Type System

  • Flat enum design: Single cudf::type_id with 29 entries
  • cudf::data_type wraps type_id + optional scale_type metadata
  • Every type explicit: No logical subclasses or overlays
  • Backing types: bool, int8–64, uint8–64, float, double, string_view
  • Unsigned integers are first-class (UINT8–64)
  • 5 timestamp precisions: days, seconds, ms, μs, ns as separate enums
  • DICTIONARY32 is a type_id (encoding in the type system)
  • No extension mechanism (Arrow extensions could bridge)
  • DECIMAL32/64/128: three decimal widths vs Velox's two

Key Differences in Detail

Unsigned Integers
cuDF has UINT8/16/32/64 as first-class types; Velox has no unsigned integer types at all. Queries producing unsigned results cannot round-trip through the Velox type system.
Timestamp Precision
cuDF has 5 resolutions (TIMESTAMP_DAYS / _SECONDS / _MILLISECONDS / _MICROSECONDS / _NANOSECONDS). Velox has a single Timestamp type storing a (seconds, nanos) pair internally, with DATE as a separate logical type on INTEGER. The bridge always emits TIMESTAMP_NANOSECONDS.
Duration / Interval
cuDF has 5 DURATION_* types. Velox has INTERVAL_DAY_TIME (milliseconds as int64, overlaid on BIGINT) and INTERVAL_YEAR_MONTH (months as int32, overlaid on INTEGER). Only partial expression-layer mapping exists for DURATION_MS; INTERVAL_YEAR_MONTH explicitly fails.
DECIMAL32
cuDF supports 32-bit fixed-point decimal; Velox skips to DECIMAL64 (ShortDecimalType on BIGINT) and DECIMAL128 (LongDecimalType on HUGEINT). The bridge never produces DECIMAL32.
Binary vs String
Velox distinguishes VARCHAR (text) and VARBINARY (binary bytes); cuDF has only STRING. The bridge maps both to STRING, losing VARBINARY identity. Round-trip is recovered via an Arrow format marker ("z") hack in the Arrow bridge path.
MAP Type
Velox has a native MAP TypeKind (key+value children); cuDF has no MAP type. It is typically represented as LIST<STRUCT<key, value>>. The bridge has commented-out MAP support.
Dictionary Encoding
cuDF treats DICTIONARY32 as a type_id. Velox handles dictionary encoding orthogonally at the vector level via DictionaryVector, independent of the type system entirely.
Extension Types
Velox supports 18 Presto extension types (UUID, JSON, IPADDRESS, HyperLogLog, sketches, etc.) via C++ subclass identity and distinct name(). cuDF has no extension type mechanism. None of these 18 types are mapped in the bridge.
Conversion Mechanism
Two paths exist: (1) Direct switch via veloxToCudfDataType() for metadata/empty tables/AST expressions, and (2) Arrow bridge via exportToArrow → cudf::from_arrow for actual data batches. There is no reverse mapping; cuDF→Velox always goes through Arrow import.
